# Story 4.1: Quiz Session Creation and State Management

## Status

**Ready for Review** - All tasks complete including question_target field (Tasks 18-23)

---

## Story

**As a** user ready to study,
**I want** to start an adaptive quiz session,
**so that** I can practice questions selected optimally for my knowledge state.

---

## Architecture Gap Resolutions

The following gaps between Epic 4.1 and architecture were identified and resolved:

| Gap | Epic Request | Resolution | Rationale |
|-----|--------------|------------|-----------|
| Session Types | `focused_ka`, `focused_concept` | Use single `focused` type | Use `knowledge_area_filter` for KA focus; concept focus deferred to Story 4.8 |
| `target_concept_ids` | JSONB column | Deferred to Story 4.8 | Focused concept sessions implemented in Story 4.8 (Focused Practice Mode) |
| `total_info_gain` | FLOAT column | Deferred to Story 4.7 | Information gain tracking needed for adaptive termination (Story 4.7) |
| `paused_at` timestamp | Explicit column | Use `updated_at` as proxy | Acceptable limitation; trigger updates `updated_at` when `is_paused` changes |
| Status enum | Explicit `status` column | Derived in application code | Architecture pattern is cleaner; see `derive_status()` in Dev Notes |
| Session uniqueness | Per user vs per enrollment | Per user globally | Better UX - users shouldn't have concurrent sessions across courses |

**Result:** Story 4.1 proceeds with current architecture. Minor schema addition required: `question_target` column for fixed-length sessions (v2.2 update).

## Acceptance Criteria (Aligned with Architecture)

Based on **current architecture**, the following ACs can be implemented:

1. POST `/api/v1/quiz/session/start` creates new quiz session
2. Session record uses existing `quiz_sessions` schema:
   - id (UUID, PK)
   - user_id (FK to users)
   - enrollment_id (FK to enrollments)
   - session_type: `'diagnostic'`, `'adaptive'`, `'focused'`, `'review'`
   - question_strategy: `'max_info_gain'`, `'max_uncertainty'`, `'prerequisite_first'`, `'balanced'`
   - knowledge_area_filter (nullable) - for focused sessions
   - **question_target (INT, default 10) - configurable for habit-forming consistency**
   - started_at, ended_at (TIMESTAMPS)
   - total_questions, correct_count (INT, default 0)
   - is_paused (BOOLEAN, default FALSE)
   - version (INT) - optimistic locking
   - updated_at (auto-managed by trigger)
3. On session start, set `question_target` to 10 (configurable default)
4. Only one active session per user (where `ended_at IS NULL`)
5. Session start triggers first question selection (Story 4.2) - placeholder
6. Response includes session_id, first question, and `question_target`
7. GET `/api/v1/quiz/session/{id}` returns session state including `question_target`
8. POST `/api/v1/quiz/session/{id}/pause` sets `is_paused = TRUE`
9. POST `/api/v1/quiz/session/{id}/end` completes session (or auto-completes when `questions_answered == question_target` per Story 4.7)
10. Sessions auto-expire after 2 hours of inactivity (based on `updated_at`)
11. Logging: Session lifecycle events tracked with structured logging

**Deferred to Later Stories:**
- Focused concept sessions with `target_concept_ids` → Story 4.8
- Information gain tracking (`total_info_gain`) → Story 4.7

### Derived Status Pattern

Architecture uses `ended_at` and `is_paused` columns instead of explicit `status` enum. Implement derived status in application code:

```python
def derive_session_status(session: QuizSession, timeout_hours: int = 2) -> str:
    """Derive session status from database columns."""
    if session.ended_at is not None:
        return "completed"

    # Check expiration based on updated_at
    timeout = timedelta(hours=timeout_hours)
    if datetime.utcnow() > session.updated_at + timeout:
        return "expired"

    if session.is_paused:
        return "paused"

    return "active"
```
