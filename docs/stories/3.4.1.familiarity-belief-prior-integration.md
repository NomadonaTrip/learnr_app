# Story 3.4.1: Familiarity-Based Belief Prior Integration

## Status

**Ready for Review**

---

## Story

**As a** system,
**I want** to use the user's declared familiarity level from onboarding to set initial belief priors,
**so that** question selection is appropriately calibrated to the user's starting knowledge level.

---

## Background

Stories 3.3 and 3.4 specify that `initialBeliefPrior` from Q3 (New→0.1, Basics→0.3, Intermediate→0.5, Expert→0.7) should be used to initialize belief states. However, the current implementation uses hardcoded `Beta(1,1)` for all users regardless of familiarity level. This story addresses that implementation gap.

---

## Acceptance Criteria

1. **Backend Schema Update:**
   - Extend `UserCreate` schema to accept optional `onboarding_data` field:
     ```python
     class OnboardingData(BaseModel):
         course: str                    # 'business-analysis'
         motivation: str                # 'certification', etc.
         familiarity: str               # 'new', 'basics', 'intermediate', 'expert'
         initial_belief_prior: float    # 0.1, 0.3, 0.5, or 0.7

     class UserCreate(BaseModel):
         email: EmailStr
         password: str
         onboarding_data: OnboardingData | None = None
     ```

2. **Registration Route Update:**
   - Pass `course_id` (from `onboarding_data.course`) and `initial_belief_prior` to belief initialization service
   - Look up course by slug/name to get `course_id`

3. **Belief Initialization Service Update:**
   - Add `initial_belief_prior: float = 0.5` parameter to `initialize_beliefs_for_user()`
   - Calculate alpha/beta from prior:
     ```python
     # Use 10 pseudo-observations for reasonable initial confidence
     pseudo_observations = 10
     alpha = prior * pseudo_observations  # e.g., 0.3 * 10 = 3
     beta = (1 - prior) * pseudo_observations  # e.g., 0.7 * 10 = 7
     ```

4. **Database Function Update:**
   - Update `initialize_beliefs(p_user_id UUID)` to accept `p_alpha FLOAT, p_beta FLOAT` parameters
   - Or create new function `initialize_beliefs_with_prior(p_user_id UUID, p_alpha FLOAT, p_beta FLOAT)`

5. **Fallback Behavior:**
   - If `onboarding_data` is null (legacy users, API-only registration), use `Beta(1,1)` as default

6. **Testing:**
   - Unit test: Prior 0.1 → alpha=1, beta=9 (or scaled equivalent)
   - Unit test: Prior 0.7 → alpha=7, beta=3 (or scaled equivalent)
   - Integration test: Full registration flow with onboarding data sets correct priors
   - Integration test: Registration without onboarding data uses default `Beta(1,1)`

7. **Migration Consideration:**
   - Existing users with `Beta(1,1)` do not need migration (their beliefs have evolved through answers)

### BKT Architecture - Prior Calculation

**Why Use Pseudo-Observations Scaling:**

The Beta distribution's α and β parameters act as "pseudo-counts" of successes and failures. Using scaled values provides reasonable initial confidence:

```python
# Prior 0.3 with 10 pseudo-observations:
alpha = 0.3 * 10 = 3  # "3 successes observed"
beta = 0.7 * 10 = 7   # "7 failures observed"
mean = 3 / (3 + 7) = 0.3  # Same as declared prior
confidence = 10 / 12 = 0.83  # Moderate confidence
```

**Alternative (Epic's Original Spec):**
```python
# alpha=prior, beta=1-prior (low confidence)
alpha = 0.3
beta = 0.7
confidence = 1 / 3 = 0.33  # Very low confidence
```

The pseudo-observations approach (used in this story) provides more stable initial beliefs that won't swing wildly on the first question.

**Confidence Formula:**
```python
def calculate_confidence(alpha: float, beta: float) -> float:
    total_evidence = alpha + beta
    return total_evidence / (total_evidence + 2)
```

### Registration Route Pattern

The current registration flow in `apps/api/src/routes/auth.py`:

```python
@router.post("/register")
async def register(user_data: UserCreate, db: AsyncSession = Depends(get_db)):
    # 1. Create user
    user, token = await auth_service.register_user(user_data.email, user_data.password)

    # 2. Initialize beliefs (currently uses hardcoded Beta(1,1))
    result = await belief_service.initialize_beliefs_via_db_function(user.id)

    return RegisterResponse(user=user, token=token)
```

**Modified Flow (This Story):**
```python
@router.post("/register")
async def register(user_data: UserCreate, db: AsyncSession = Depends(get_db)):
    # 1. Create user
    user, token = await auth_service.register_user(user_data.email, user_data.password)

    # 2. Extract onboarding data (if present)
    if user_data.onboarding_data:
        course = await course_repo.get_course_by_slug(user_data.onboarding_data.course)
        course_id = course.id if course else default_course_id
        prior = user_data.onboarding_data.initial_belief_prior
    else:
        # Fallback: No onboarding data (legacy/API-only registration)
        course_id = default_course_id
        prior = None  # Triggers Beta(1,1) fallback in service

    # 3. Initialize beliefs with prior (or fallback to Beta(1,1))
    result = await belief_service.initialize_beliefs_for_user(
        user_id=user.id,
        course_id=course_id,
        initial_belief_prior=prior  # None triggers Beta(1,1) fallback
    )

    return RegisterResponse(user=user, token=token)
```
