# Story 5.9: Reading Queue Analytics and Completion Rates

## Status

**Approved**

## Story

**As a** product team,
**I want to** track reading queue engagement metrics,
**so that** we can validate the async reading model improves completion rates vs. inline reading.

## Acceptance Criteria

1. GET `/api/v1/reading/stats` endpoint returns complete user-level reading analytics
   - **Response schema:**
   ```json
   {
     "reading_stats": {
       "total_items_added": 45,
       "total_completed": 28,
       "total_dismissed": 10,
       "current_unread": 7,
       "completion_rate": 0.62,
       "this_week": {
         "items_added": 7,
         "items_completed": 5,
         "total_reading_time_minutes": 25
       },
       "by_ka": [
         {
           "ka_name": "Business Analysis Planning and Monitoring",
           "unread": 3,
           "completed": 8,
           "completion_rate": 0.73
         }
       ],
       "average_reading_time_minutes": 2.5,
       "total_reading_time_hours": 1.2
     }
   }
   ```
   - Target: `completion_rate` >0.50 (50%+ per PRD v2.1 success criteria)
2. Dashboard integration: Display reading stats on main dashboard
   - "Reading Progress: X completed (Y% completion rate)"
   - "Total Reading Time: Z minutes"
3. Admin analytics endpoint GET `/api/admin/alpha-metrics/reading`:
   - Platform-wide reading completion rate
   - Comparison: Async model (v2.1) vs. Inline model (v2.0 baseline, if A/B tested)
   - Average reading time per chunk
   - Most frequently added BABOK sections (helps identify high-value content)
4. Track reading engagement by priority:
   - High priority items: Completion rate (expect highest)
   - Medium priority: Completion rate
   - Low priority: Completion rate (expect lowest)
5. Hypothesis validation metrics (Day 24 alpha test):
   - Async reading completion rate >50% (vs. 25% inline baseline per PRD)
   - User satisfaction with "read when ready" model (survey question)
6. Spaced repetition integration: Items marked "completed" should not re-appear in queue (unique constraint enforced)
7. Retention analysis: Users who complete reading have better long-term retention (tracked via spaced repetition accuracy)
8. Unit tests: Analytics calculations accurate
9. Integration test: Reading completion updates all analytics metrics
10. Performance: Analytics queries optimized with indexes on `reading_queue(enrollment_id, status)`

**AC Implementation Notes:**
- **AC 5 (Hypothesis validation):** Measurement criterion - validated via admin dashboard metrics (Task 4). Survey question tracked separately.
- **AC 6 (Spaced repetition):** Already enforced by `UNIQUE (enrollment_id, chunk_id)` constraint in `reading_queue` table (database-schema.md:355). No additional implementation required.
- **AC 7 (Retention analysis):** Deferred to post-MVP analytics phase. Requires correlation between reading completion and spaced repetition accuracy data that will be available after sufficient user data collection. **Tracked in:** Future Epic "Advanced Learning Analytics" (to be created after Day 24 alpha test data collection).

### Analytics Calculations

**Completion Rate Formula:**
```python
completion_rate = completed_count / (completed_count + dismissed_count)
# Note: current_unread items are not included in rate calculation
# as they may still be completed
```

**Weekly Stats Query (SQL):**
```sql
SELECT
    COUNT(*) FILTER (WHERE added_at >= NOW() - INTERVAL '7 days') AS items_added,
    COUNT(*) FILTER (WHERE completed_at >= NOW() - INTERVAL '7 days') AS items_completed,
    COALESCE(SUM(total_reading_time_seconds) FILTER (
        WHERE completed_at >= NOW() - INTERVAL '7 days'
    ), 0) / 60 AS total_reading_time_minutes
FROM reading_queue
WHERE enrollment_id = :enrollment_id;
```

### Technical Constraints

- **Performance:** Analytics queries should complete in <500ms
- **Caching (Admin Endpoint):**
  - Redis key: `reading:admin:metrics`
  - TTL: 300 seconds (5 minutes)
  - Invalidation: Time-based expiry only (no event-based invalidation needed for aggregate metrics)
  - Fallback: If Redis unavailable, query database directly (log warning)
- **Indexes:** Required on `(enrollment_id, status)`, `(enrollment_id, added_at)`
- **Timezone Handling:**
  - All timestamps stored and queried in UTC
  - Weekly stats use server-side UTC calculation (`NOW() - INTERVAL '7 days'`)
  - Frontend formats timestamps to user's locale for display (use `Intl.DateTimeFormat`)
[Source: architecture/tech-stack.md]
