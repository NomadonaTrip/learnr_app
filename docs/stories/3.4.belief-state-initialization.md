           beta=1.0,   # Beta(1,1) = Uniform[0,1]

5. Idempotent: If belief states already exist, skip (handle retry scenarios)

7. Database indexes support efficient per-user queries
8. Error handling: Transaction rollback on failure, user notified
9. **No beliefs should have NULL values** - all concepts tracked from start
10. API endpoint: GET `/api/v1/beliefs/stats` returns initialization status

### BKT Architecture - Initial Belief Seeding

**Uninformative Prior: Beta(1,1)**

LearnR uses Bayesian Knowledge Tracing (BKT) to model user mastery as probability distributions. For new users, we start with an **uninformative prior**: Beta(1,1), which represents uniform uncertainty.

**Mathematical Foundation:**

```python
# Beta(1,1) = Uniform[0,1]
# Mean = alpha / (alpha + beta) = 1 / 2 = 0.50 (no idea if they know it)
# Confidence = (alpha + beta) / (alpha + beta + 2) = 2 / 4 = 0.50 (low confidence)
```

This means: "We have no information about this user's knowledge of this concept. It could be anywhere from 0% to 100% mastery."

**Why Beta(1,1)?**

1. **Bounded [0,1]:** Probabilities must be between 0 and 1
2. **Conjugate Prior:** Bayesian updates preserve Beta distribution form
3. **Two Parameters:** α and β capture both estimate and confidence
4. **Uninformative:** No bias toward mastery or non-mastery

[Source: docs/architecture/bkt-architecture.md#mathematical-primer]

**Core Algorithm:**

```python
async def initialize_beliefs(user_id: UUID, concepts: List[Concept]) -> None:
    """
    Initialize belief states for a new user.

    Uses uninformative prior: Beta(1, 1) = Uniform[0, 1]
    This represents "we know nothing about this user's knowledge."
    """
    belief_states = []

    for concept in concepts:
        belief_states.append(BeliefState(
            user_id=user_id,
            concept_id=concept.id,
            alpha=1.0,  # Uninformative prior
            beta=1.0,   # Uninformative prior
            response_count=0
        ))

    await belief_repository.bulk_create(belief_states)
```

### Database Schema - belief_states Table

**Table Definition:**

```sql
CREATE TABLE belief_states (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    concept_id UUID NOT NULL REFERENCES concepts(id) ON DELETE CASCADE,
    alpha FLOAT NOT NULL DEFAULT 1.0,
    beta FLOAT NOT NULL DEFAULT 1.0,
    last_response_at TIMESTAMP,
    response_count INTEGER NOT NULL DEFAULT 0,
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMP NOT NULL DEFAULT NOW(),
    UNIQUE (user_id, concept_id),
    CHECK (alpha > 0),
    CHECK (beta > 0)
);

CREATE INDEX idx_belief_states_user ON belief_states(user_id);
CREATE INDEX idx_belief_states_user_concept ON belief_states(user_id, concept_id);
CREATE INDEX idx_belief_states_updated ON belief_states(updated_at);
```

**Database Function (Already Defined):**

```sql
CREATE OR REPLACE FUNCTION initialize_beliefs(p_user_id UUID)
RETURNS INTEGER AS $$
DECLARE
    inserted_count INTEGER;
BEGIN
    INSERT INTO belief_states (user_id, concept_id, alpha, beta)
    SELECT p_user_id, id, 1.0, 1.0
    FROM concepts
    ON CONFLICT (user_id, concept_id) DO NOTHING;

    GET DIAGNOSTICS inserted_count = ROW_COUNT;
    RETURN inserted_count;
END;
$$ LANGUAGE plpgsql;
```

**Key Constraints:**

- UNIQUE (user_id, concept_id) - prevents duplicate beliefs
- CHECK (alpha > 0, beta > 0) - ensures valid Beta distribution
- ON DELETE CASCADE - cleanup on user deletion

### Performance Requirements

**Bulk Insert Optimization:**

Use SQLAlchemy `bulk_insert_mappings` for performance:

```python
# Good - Bulk insert (single database round-trip)
await session.run_sync(
    lambda sess: sess.bulk_insert_mappings(
        BeliefState,
        belief_dicts
    )
)

# Bad - Individual inserts (N database round-trips)
for belief in beliefs:
    session.add(belief)
await session.commit()
```

**Performance Target:** 1500 concepts initialized in <2 seconds

**Optimization Strategies:**

1. Use `bulk_insert_mappings` (not `session.add()` loop)
2. Single transaction (commit once, not per record)
3. Disable autoflush during bulk insert
4. Consider PostgreSQL COPY if bulk insert still slow

### Idempotency Handling

**Challenge:** Network retries or bugs may cause duplicate initialization attempts.

**Solution:** Check if already initialized before inserting:

```python
async def initialize_beliefs_for_user(self, user_id: UUID) -> InitializationResult:
    """Initialize beliefs (idempotent)."""

    # Check if already initialized
    existing_count = await belief_repo.get_belief_count(user_id)
    if existing_count > 0:
        logger.info(
            "Beliefs already initialized, skipping",
            user_id=str(user_id),
            existing_count=existing_count
        )
        return InitializationResult(
            success=True,
            already_initialized=True,
            belief_count=existing_count
        )

    # Proceed with initialization...
```

**Database-Level Idempotency:**

Use `ON CONFLICT DO NOTHING` in SQL:

```sql
INSERT INTO belief_states (user_id, concept_id, alpha, beta)
SELECT p_user_id, id, 1.0, 1.0
FROM concepts
ON CONFLICT (user_id, concept_id) DO NOTHING;
```
