# Story 4.8: Focused Practice Mode

## Status

**Ready** (PO Re-Validated 2025-12-29 v1.4)

## Story

**As a** user,
**I want** to practice questions focused on specific concepts or knowledge areas,
**so that** I can target my weak areas.

## Acceptance Criteria

1. POST `/api/v1/quiz/session/start` accepts:
   ```json
   {
     "session_type": "focused_ka",
     "knowledge_area_filter": "elicitation"
   }
   ```
   or:
   ```json
   {
     "session_type": "focused_concept",
     "target_concept_ids": ["uuid1", "uuid2"]
   }
   ```
2. Question selector filters to target KA or concepts
3. Still uses info-gain within filtered set
4. UI shows focus context: "Practicing: Elicitation and Collaboration"
5. **Gap-based suggestions:**
   - "You have 15 gap concepts in Requirements Analysis. Focus on these?"
   - Quick-start focused session from coverage report
6. Session tracks target achievement:
   - Did beliefs improve for target concepts?
   - Did any flip from gap to mastered?
7. End-of-session summary shows target progress
8. Fallback: If target exhausted, expand to prerequisites or suggest different focus
9. Unit tests: Filter by KA, filter by concept
10. Integration test: Focused session only asks relevant questions

### Design Decisions

**Session Type Strategy:**
- `FOCUSED` (existing): Kept for backward compatibility with existing focused sessions
- `FOCUSED_KA` (new): Explicit KA-focused mode, uses existing `knowledge_area_filter` field
- `FOCUSED_CONCEPT` (new): Concept-focused mode, uses new `target_concept_ids` field

**Field Reuse for FOCUSED_KA:**
- Do NOT add a separate `target_ka_id` field to the schema
- Reuse the existing `knowledge_area_filter` field for `FOCUSED_KA` sessions
- The validator ensures `knowledge_area_filter` is provided when `session_type == FOCUSED_KA`
- This avoids redundant fields and maintains consistency with existing focused session behavior

**Column Type for target_concept_ids:**
- Use `JSONB` (not `ARRAY(UUID)`) for consistency with existing patterns (e.g., `options` in questions table)
- JSONB provides flexibility for future metadata and better PostgreSQL indexing support
- Store as: `["uuid1", "uuid2", "uuid3"]`

**Error Handling:**
- Invalid `knowledge_area_filter` (KA doesn't exist in course): Return 400 with message "Invalid knowledge area: {ka_id}"
- Invalid `target_concept_ids` (concepts don't exist or not in course): Return 400 with message "Invalid concept IDs: {ids}"
- Empty `target_concept_ids` for FOCUSED_CONCEPT: Return 400 with message "target_concept_ids required for focused_concept sessions"

### UI/UX Design Decisions

**Dashboard Primary Actions:**
The dashboard has two primary user actions that should remain prominent:
1. **"Start Adaptive Quiz"** - The main learning action
2. **"See Reading Library"** - Access to reading materials

Focused practice is a **secondary action** and should not compete with these primary CTAs.

**Entry Points for Focused Practice (Two Locations on Existing Dashboard):**

| Location | Element | Behavior |
|----------|---------|----------|
| KA Competence Rows | "Focus" button | In-context action, starts `focused_ka` session |
| Gap Concept List | "Practice" button + multi-select | Single or batch concept targeting via `focused_concept` session |

**Rejected Approach - Toolbar Button:**
A dedicated "Focused Practice" toolbar button was considered but rejected because:
- It's an **abstraction without context** - users still need to select what to focus on
- Requires users to learn a new mental model ("focused practice" as a concept)
- Saves only one navigation step but adds cognitive overhead
- Duolingo's model is different: their skills ARE the focus areas (no separate abstraction)

**Enhance Existing Dashboard Elements (Simplest Approach):**
The dashboard already displays KA competence levels and gap concepts. Rather than adding new components, add action buttons to existing elements:

**KA Competence Row - Add Focus Button:**
```
│  Elicitation    ━━━━━━░░░░  44%    [Focus]  │
                                        ↑ visible when gaps > 0
```

**Gap Concept List - Add Practice Buttons:**
```
│  ☐ Stakeholder Identification (32%)  [Practice]  │
│  ☐ Interview Techniques (28%)        [Practice]  │
│  ☐ Requirements Validation (41%)     [Practice]  │
│                                                   │
│  [Practice Selected (0)]                          │
```

**Why this approach:**
- No new components to build - enhance what exists
- Users already understand the dashboard layout
- Action buttons appear in context where data is shown
- As gaps close, cards disappear (satisfying progress)
- Multi-select enables power users to target specific concepts

**Gap Card Removal Threshold:**
- Concept cards disappear from gap list when P(mastery) ≥ 0.5
- Consistent with system's gap classification (gap = P(mastery) < 0.5 with confidence ≥ 0.7)
- KA "Focus" buttons disappear when that KA has zero gap concepts remaining

```python
from pydantic import model_validator

class QuizSessionCreate(BaseModel):
    session_type: QuizSessionType = Field(default=QuizSessionType.ADAPTIVE)
    question_strategy: QuestionStrategy = Field(default=QuestionStrategy.MAX_INFO_GAIN)
    knowledge_area_filter: str | None = Field(default=None)  # Reused for FOCUSED_KA
    # NEW field for concept-focused mode only
    target_concept_ids: list[UUID] | None = Field(
        default=None,
        description="Target concept IDs for focused_concept sessions"
    )

    @model_validator(mode='after')
    def validate_focused_targets(self) -> 'QuizSessionCreate':
        if self.session_type == QuizSessionType.FOCUSED_KA:
            if not self.knowledge_area_filter:
                raise ValueError("knowledge_area_filter required for focused_ka sessions")
        if self.session_type == QuizSessionType.FOCUSED_CONCEPT:
            if not self.target_concept_ids or len(self.target_concept_ids) == 0:
                raise ValueError("target_concept_ids required for focused_concept sessions")
        return self
```

### Question Selector Extensions

**Concept Filtering Logic:** [Source: services/question_selector.py]

```python
async def select_next_question(
    self,
    user_id: UUID,
    session_id: UUID,
    beliefs: Dict[UUID, BeliefState],
    available_questions: List[Question],
    strategy: str = "max_info_gain",
    knowledge_area_filter: str | None = None,
    target_concept_ids: list[UUID] | None = None,  # NEW
) -> Tuple[Question | None, float, dict]:
    """
    Select optimal next question with optional filtering.

    Returns:
        Tuple of (question, info_gain, metadata)
        metadata includes: filtered_count, fallback_used, exhausted
    """
    candidates = available_questions

    # Apply KA filter
    if knowledge_area_filter:
        candidates = [q for q in candidates if q.knowledge_area_id == knowledge_area_filter]

    # Apply concept filter (NEW)
    if target_concept_ids:
        target_set = set(target_concept_ids)
        candidates = [
            q for q in candidates
            if any(qc.concept_id in target_set for qc in q.question_concepts)
        ]

    # Check if filtered set is exhausted
    if not candidates:
        # Fallback: expand to prerequisites of target concepts
        if target_concept_ids:
            prereq_ids = await self._get_prerequisites(target_concept_ids)
            candidates = [
                q for q in available_questions
                if any(qc.concept_id in prereq_ids for qc in q.question_concepts)
            ]
            if candidates:
                return self._select_by_info_gain(candidates, beliefs), {"fallback_used": "prerequisites"}

        return None, 0.0, {"exhausted": True, "suggest_different_focus": True}

    # Use info-gain within filtered set
    return self._select_by_info_gain(candidates, beliefs), {"filtered_count": len(candidates)}
```

### Technical Constraints

**Focus Session Rules:** [Source: epic-4-bkt.md]

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| Max target concepts | 20 | Prevent overly narrow focus |
| Min questions before exhaust | 5 | Need data before suggesting fallback |
| Prerequisite expansion depth | 1 level | Don't expand too far |

**Note on question_target Constraint:**
The existing `quiz_sessions.question_target` column has a CHECK constraint: `BETWEEN 10 AND 15`. Focused sessions use this same constraint. If focused sessions need different target limits, the migration in Task 2 should also update this constraint. For MVP, the 10-15 range is acceptable for focused sessions.

**Design System:** [Source: architecture/frontend-architecture.md]

- Border radius: 14px for cards
- Font: Inter
- KA colors from course.knowledge_areas[].color
- Focus banner should use subtle background with KA accent

**Coding Standards:** [Source: architecture/coding-standards.md]

- Python functions: snake_case
- TypeScript functions: camelCase
- Service layer for all API calls
- Use structlog for backend logging
- Use React Query for data fetching
